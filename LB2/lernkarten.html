Grundlagen & Vorgehensmodelle

FehlerEine Anforderung wird nicht erfüllt: IST ≠ SOLL. Beispiel: 3 × 10 CHF ergibt 20 CHF.
MangelAnforderung oder berechtigte Erwartung wird nicht angemessen erfüllt. Beispiel: Rechnung stimmt, wird aber als 30.000000001 angezeigt.
  • Fehlermaskierung: Ein Fehler wird von einem anderen Programmteil ausgeglichen und ist deshalb nicht sichtbar. Er zeigt sich erst, wenn der andere Teil korrigiert wird, oder später (z.B. falsch gespeicherte Daten).
  • Vollständiges Testen ist unmöglich: Testen kann Fehlerfreiheit nicht beweisen. Es gibt zu viele Kombinationen von Eingaben und Randbedingungen.
  • Gute Testfälle: hohe Wahrscheinlichkeit, Fehler zu finden · keine Redundanz · unabhängig voneinander · decken möglichst viel Code ab.
  • Testaufwand: muss zum möglichen Schaden passen. Hoher Schaden (Geld, Menschenleben) → mehr testen. Beispiele: Ariane 5, Therac-25.
  • Testabdeckung (Code Coverage): wie viel vom Code die Tests ausführen (Zeilen, Verzweigungen). Tools: JaCoCo, IntelliJ „Run with Coverage“. 100 % heisst nicht fehlerfrei.

Testlevels

Reihenfolge: Unit → Component → Integration → System → Acceptance. Jede Stufe ist langsamer und kommt später im Prozess. Unit-, Component- (und teils Integrationstests) laufen beim Build.

LevelWerBoxWas
UnitEntwicklerWhiteEine Klasse/Methode isoliert. Schnell, gibt Sicherheit fürs Refactoring, vor allem funktional. Grenze: isoliert ok heisst nicht, dass es zusammen funktioniert.
ComponentEntwicklerWhiteZusammenspiel mehrerer Komponenten. Schnittstellen (DB, externe APIs, Message Queues) werden gemockt.
IntegrationTester / QA (teils Entwickler)Black + WhiteDB, APIs, Queues werden echt benutzt, nicht mehr gemockt.
Systemgleiche Teams wie IntegrationBlackGanze Software in einer Live-nahen Umgebung. Funktional + nicht-funktional: Load, Stress, Usability, Security.
AcceptanceKunde / BusinessBlackErfüllt das System die Akzeptanzkriterien? (UAT)
  • Load Testing: Verhalten bei einer festgelegten Anzahl Requests. Stress Testing: das Limit der Software finden.
  • Abkürzungen: UAT = User Acceptance Testing, QA = Quality Assurance, SLA = Service Level Agreement.

Unit Testing (JUnit 5)

Rolle von Unit-Tests

  • steuern eher das Design, als Fehler zu finden
  • halten Code langfristig änderbar
  • Voraussetzung fürs Refactoring
  • decken versehentliche Änderungen sofort auf
  • dokumentieren das System

Gute Unit-Tests

  • isoliert, Reihenfolge egal
  • prüfen genau eine Eigenschaft
  • vollautomatisch, schnell, wiederholbar
  • kurz und verständlich, gleiche Codequalität wie Produktivcode
  • testen relevanten Code (keine Getter/Setter)
  • idealerweise vor dem Code geschrieben (TDD)

F.I.R.S.T.: Fast, Independent, Repeatable, Self-validating, Timely.

Schnittstellen & Test Doubles

Ein Test Double ersetzt im Test etwas Echtes, wie ein Stunt-Double. Damit schaltet man Abhängigkeiten aus, die im Test nicht interessieren. SUT = System under Test.

Mock (mock, spy)Behavioral testing. Prüft, ob das SUT ihn richtig aufgerufen hat.
Stub (stub, dummy, fake)State testing. Liefert Daten ans SUT, danach prüft man das Ergebnis.
DoubleWas es machtBeispiel
MockErwartungen setzen, SUT aufrufen, prüfen ob die Methode aufgerufen wurdeverify(repo).save(a)
Spyzeichnet still alle Aufrufe auf, du prüfst danach selbstMockito spy(...)
Dummywird nur übergeben (z.B. Konstruktor füllen), keine Methodennull als Parameter
Stubvordefinierte, hardcodierte Antwortenwhen(repo.findAll()).thenReturn(list)
Fakefunktionierende, vereinfachte ImplementierungIn-Memory-Repository statt DB

Lifecycle Stub

  2. Anwenden
  3. Verify state
  4. Teardown

Lifecycle Mock

  1. Daten einrichten
  2. Setup expectations
  3. Anwenden
  4. Verify expectations

Frameworks: Mockito (kann Mock, Spy, Stub, Dummy), WireMock (HTTP-Mock-Server, um APIs zu mocken).

Code Reviews

Code Review = Vier-Augen-Prinzip: eine zweite Person prüft jede Implementierung, stellt Fragen, korrigiert und gibt am Schluss ihr OK. Pull Request (GitHub, Bitbucket) heisst bei GitLab Merge Request. Das ist eine Konvention der Hosting-Dienste, kein Git-Feature.

Ablauf

  1. Feature-Branch erstellen: git checkout -b feature
  2. Implementieren, git add ., git commit -m "..."
  3. Pushen: git push --set-upstream origin feature
  4. PR erstellen: Titel, Beschreibung, Reviewer wählen
  5. Review: Kommentare, diskutieren, Feedback einbauen (neue Commits aktualisieren den PR)
  6. Approve → Merge in main (GitLab: standardmässig Merge-Commit, es gibt auch Squash / Fast-forward)

Grösse: 200–400 geänderte Zeilen, 60–90 Minuten Review (SmartBear-Studie bei Cisco). Grosse PRs bekommen weniger Kommentare, also klein halten.

Worauf achten

  • zu viele / zu wenige Kommentare
  • konsistentes Naming
  • Logikfehler, Typos
  • lange, komplizierte Zeilen
  • unnötiger Code gelöscht
  • Tests vorhanden und vollständig
  • YAGNI, DRY, KISS, SRP
  • Code gepflegter als vorher

Prinzipien

  • YAGNI: nur das Nötige, nicht vergolden
  • DRY: nichts doppelt
  • KISS: einfach halten
  • SRP: jede Klasse ist nur für eine Sache zuständig

Sozial

  • nett, professionell, konstruktiv, ausführlich
  • nicht alles nach eigenem Geschmack, sondern als Vorschlag
  • Themen ausserhalb des Features → Follow-up-Ticket
  • „Don’t be a jerk“

Im Modul gilt: Das Review macht das Team, KI ersetzt das Vier-Augen-Prinzip nicht.

Test Driven Development

Die Tests treiben das Schreiben des Codes. Mantra: zuerst einen Test schreiben, der fehlschlägt, bevor eine Zeile „richtiger“ Code entsteht. Seit ca. 2003, Teil von Agile / Extreme Programming. Ron Jeffries: „Clean code that works“.

RedTest schreiben, der fehlschlägt (es gibt noch keinen Code).
GreenMinimalen Code schreiben, bis der Test grün ist.
RefactorCode und Tests verbessern, ohne das Verhalten zu ändern. Dann wieder Red.
  • Iterativ: jeder Test prüft eine Logik und ein Szenario, also mehrere Tests pro Logik.
  • Best Practices: Anforderungen verstehen · atomare Tests · einfachsten Test zuerst · Randfälle testen · regelmässig refactoren · schnelle Feedbackschleife · Tests automatisieren · Red-Green-Refactor einhalten · in CI laufen lassen.
  • Vorteile: lose gekoppelter, modularer Code · weniger Kosten · Refactoring einfacher · Onboarding einfacher · weniger Bugs und Kopplung · bessere Zusammenarbeit · Vertrauen in den Code · keine Angst vor Änderungen.
  • Nachteil: schwierig in Projekten, die nicht von Anfang an mit TDD gemacht wurden.
Leertaste = Antwort · → gewusst · ← nochmal

Grundgerüst Testklasse

class CalculatorTest {

    private Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();          // frisch für jeden Test
    }

    @Test
    @DisplayName("Zwei Zahlen addieren")
    void add() {
        // Arrange - Act - Assert
        double result = calculator.add(2, 3);
        assertEquals(5, result);                // erwartet, tatsächlich
    }

    @Test
    void divideByZeroThrows() {
        assertThrows(ArithmeticException.class, () -> calculator.divide(1, 0));
    }

    @ParameterizedTest
    @CsvSource({ "14999.95, 0", "15000, 5", "25000, 8.5" })
    void discount(double price, double expected) {
        assertEquals(expected, new DiscountCalculator().getDiscountPercent(price));
    }

    @ParameterizedTest
    @ValueSource(doubles = { -1, -100 })
    void negativeThrows(double price) {
        assertThrows(IllegalArgumentException.class,
                () -> new DiscountCalculator().getDiscountPercent(price));
    }
}

@ExtendWith(MockitoExtension.class)        // sonst sind die @Mock-Felder null
class TransferServiceTest {

    @Mock AccountRepository repository;      // Ersatz für die DB
    @Mock NotificationService notifier;
    @InjectMocks TransferService service;    // echtes SUT, bekommt die Mocks

    @Test
    void transfer() {
        Account a = new Account(1, "Muster", 500);
        Account b = new Account(2, "Gates", 100);
        when(repository.findById(1)).thenReturn(Optional.of(a));   // STUB
        when(repository.findById(2)).thenReturn(Optional.of(b));

        assertTrue(service.transfer(1, 2, 200));
        assertEquals(300, a.getBalance());

        verify(repository).save(a);                                 // MOCK
        verify(notifier).send(eq("Gates"), anyString());
        // verify(repository, never()).save(any());   verifyNoInteractions(notifier);
    }
}
